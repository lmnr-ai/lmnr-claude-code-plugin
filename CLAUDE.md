# lmnr-claude-code-plugin

Laminar observability plugin for Claude Code. Stop/SessionEnd hooks parse the session transcript incrementally and export spans to Laminar as OTLP/HTTP/JSON (OpenTelemetry's OTLP HTTP exporter; spans and batching are our own). Written in TypeScript, shipped as a single committed `dist/hook.cjs` bundle run on Node.

## Layout

- `.claude-plugin/plugin.json` — plugin manifest (no `userConfig`; the plugin is config-file-driven and installs with zero prompts, symmetric with the Codex plugin).
- `.claude-plugin/marketplace.json` — marketplace manifest so `claude plugin marketplace add lmnr-ai/lmnr-claude-code-plugin` works.
- `hooks/hooks.json` — wires Stop + SessionEnd to `node ${CLAUDE_PLUGIN_ROOT}/dist/hook.cjs`.
- `dist/hook.cjs` — **committed** esbuild bundle (all deps inlined). This is what the hooks run; end users install nothing. Rebuild + commit after any `src/` change (`npm run build`).
- `src/` — the hook, split by concern:
  - `hook.ts` — entrypoint: read the stdin payload (`session_id`, `transcript_path`, `hook_event_name`, `last_assistant_message`), run the pipeline, always exit 0.
  - `config.ts` — config + logging: API key + base URL come from `~/.config/lmnr/claude-code-plugin.json` (written by `lmnr-cli plugin add claude-code`), with `LMNR_PROJECT_API_KEY`/`LMNR_BASE_URL` env as overrides; `user_id` from `LMNR_USER_ID` env or `credentials.json`. Tunables (`CC_LMNR_DEBUG`, `CC_LMNR_MAX_CHARS`, `CC_LMNR_CAPTURE_SKILL_CONTENT`), `stateDir()` (overridable via `CC_LMNR_STATE_DIR`), size-rotated `debug`/`info` log.
  - `pipeline.ts` — one hook run (`processTranscript`): re-read from the commit offset, decide which turns are ready, render, export, save state.
  - `state.ts` — per-session state file + O_EXCL lock (`withSessionLock`), one-time migration from the legacy shared `lmnr_state.json`.
  - `transcript.ts` — row helpers, offset-aware JSONL reading (`readLines`), task-notification parsing, subagent transcript discovery (`findSubagents`).
  - `turns.ts` — split rows into turns at real prompts (`splitTurns`), move late task-notifications to the launching turn (`routeNotifications`), readiness (`pendingAgents`, `isIncomplete`).
  - `render.ts` — Turn → spans (root/LLM/tool/subagent): reads a turn's rows into the message sequence the model saw, then emits spans.
  - `genai.ts` — `gen_ai.*` wire-format serialization (Anthropic Messages API messages, usage) via `buildGenerationAttributes`, `buildUserMessage`, `toolResultBlock`.
  - `tools.ts` — `ToolTimeline`: which tool definitions each generation was offered, read from Claude Code's internal `prompt_snapshot` / `deferred_tools_record` attachment rows.
  - `otlp.ts` — span minting (`Tracer`), conversion to the SDK's `ReadableSpan` (`toReadableSpan`), and export via `OTLPTraceExporter`.
- `tests/` — `node:test` suite run via `tsx --test`. `helpers.ts`'s `TestSession` writes a transcript (and subagent transcripts) to a temp dir and runs real hook runs (`stop`/`end`) with the export captured; most tests are black-box over that.

## Development

- Install dev deps: `npm install` (`esbuild`, `tsx`, `typescript`, `@types/node`, and the `@opentelemetry/*` exporter packages pinned to exact versions — all build/test-time only: esbuild inlines the exporter, the shipped artifact is `dist/hook.cjs`).
- Run tests: `npm test` (`tsx --test tests/*.test.ts`). Typecheck: `npm run typecheck`.
- Build the runtime bundle: `npm run build` (esbuild → `dist/hook.cjs`, CJS, deps inlined, ~105 KB). Keep `--main-fields=module,main`: it bundles the OTel packages' ESM builds, which tree-shake; their CJS builds drag in the metrics SDK and all of semantic-conventions (~600 KB). **Commit `dist/hook.cjs`** — plugins install into a versioned, CLI-managed cache dir (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`) recreated on every update, so a user-run `npm install` would not survive updates. Committing the bundle means the plugin works with zero install after add AND after every update. Do NOT switch the hook back to `tsx src/hook.ts` (would require `node_modules` in the cache dir).

## OTLP / Laminar ingestion gotchas (verified against app-server)

- Emission (`otlp.ts`): our `Tracer` mints plain spans (random 32-hex trace / 16-hex span ids, epoch-ms times); `exportSpans` converts them to `ReadableSpan` (`toReadableSpan`: `kind` INTERNAL, status OK) and sends one request through `@opentelemetry/exporter-trace-otlp-http` (JSON, not protobuf/gRPC) to `{base}/v1/traces` with `Authorization: Bearer <project api key>`. The exporter retries 429/502/503/504 with backoff, all within `timeoutMillis` = `EXPORT_TIMEOUT_MS`. No tracer provider or span processor: `BatchSpanProcessor` (incl. lmnr-ts's size-limited one) can send batches at once and doesn't report each one's outcome, while the commit offset needs exactly that (see `exportInBatches`).
- The exporter merges `OTEL_EXPORTER_OTLP_*` env config (headers, certificates, timeout, compression) into its own, and Claude Code passes its own telemetry settings to hooks in exactly those vars — so `exportSpans` deletes them from the hook process first (pinned by a test). Otherwise e.g. the user's collector API key in `OTEL_EXPORTER_OTLP_HEADERS` would be sent to Laminar.
- Integer attribute values go out as JSON **numbers** (`{"intValue": 10}`), as the OTel JS JSON serializer emits them; app-server's JSON decoder accepts `intValue` as a number or a string. Non-integer numbers are `doubleValue`, null/undefined attributes are dropped (pinned by the OTLP payload test).
- `LMNR_SPAN_CONTEXT` may carry a serialized Laminar span context from a caller (`Laminar.serialize_span_context()` / SDK equivalent). When present and valid, Claude Code turn root spans use it as their remote parent, joining the caller's trace; when absent/invalid, standalone trace behavior is preserved.
- Spans are one Laminar trace per Claude Code turn, grouped into a session via `lmnr.association.properties.session_id` on the root span; `user_id` also goes on the root. Trace-constant context (`source`, `os`, `cwd`, `git_branch`, `claude_code_version`, `turn_number`, `transcript`, `skills`) goes in `lmnr.association.properties.metadata.*`. No `tags` are emitted. NEVER put per-span details in metadata — the app-server flattens those keys into TRACE-level metadata across ALL spans (last write wins). Use plain span attributes (e.g. `claude_code.tool.name`) for span-scoped data.
- LLM spans: `lmnr.span.type=LLM`, `gen_ai.input.messages` / `gen_ai.output.messages` as JSON strings in **Anthropic Messages API shape** — the transcript's own blocks (`text`, `thinking`, `tool_use`; tool results as `tool_result` blocks in a user message), bounded: strings truncated to `MAX_CHARS`, thinking signatures dropped, empty thinking skipped, images/documents replaced by `[image]`/`[document]` markers. Each generation's input is the turn's history up to it (`renderConversation` keeps it); app-server stores messages by content hash, so repeated history costs ~nothing. Don't convert to OpenAI-style `role: "tool"` / `tool_calls`: the frontend detects Anthropic content blocks natively, and the earlier OpenAI-like shape (inherited from the Langfuse plugin, with flat `tool_calls`) matched no parser and rendered empty. Usage via `gen_ai.usage.{input_tokens,output_tokens,cache_read_input_tokens,cache_creation_input_tokens}`.
- Tool definitions go on each LLM span as `gen_ai.tool.definitions` (Anthropic `{name, description, input_schema}`); app-server stores the array once by hash, so repeating it per span is cheap. Source: Claude Code's **internal, undocumented** attachment rows — `prompt_snapshot.tools` (inline tools as `{name, description, schema}`; written only when the set changes, and `null` on a transcript's first request) and `deferred_tools_record.entries` (deferred tools — MCP and some built-ins — once ToolSearch loads them). `ToolTimeline` maps them to "set in effect from timestamp T"; a generation before the first recorded set gets that first set. Because snapshots appear only on change (a resumed process records none), session state keeps the `(timestamp, hash)` changes (`toolSetChanges`) and each set is stored once in `<stateDir>/lmnr_tool_sets/<hash>.json`, pruned after 30 days unused — never the sets themselves in the session state file. A set's mtime is its last use: saving *or loading* it touches it, since a session whose set never changes only loads it. If the latest set's file is gone, the timeline's base is unknown: `deferred_tools_record` rows are skipped until the next `prompt_snapshot`, rather than persisting a set without the inline tools. Subagents build their own in-memory timeline from their transcript (their tool set differs). Unknown shapes are skipped: the span then has no tool definitions. The snapshot's `systemPrompt` is deliberately not sent (it carries the user's memory instructions, home directory and environment).
- Spans are backdated to transcript timestamps (epoch ms on `Span.startMs`/`endMs`; an end before the start clamps to it). When verifying in ClickHouse, filter `start_time` by the session's era, not the export time; the `spans` table has no `created_at`. Trace rows live in `traces_replacing` (query with `FINAL`).

## Hook behavior invariants

- Fail-open: the hook must always exit 0; a Laminar outage must never block Claude Code. Each export request, retries included, is capped by the exporter's `timeoutMillis` (`EXPORT_TIMEOUT_MS`) so a hung connection can't stall the session.
- **Commit offset, not held rows.** Per-session state (`<stateDir>/lmnr_sessions/<sha256(sessionId::transcriptPath)>.json`, `stateDir` = `~/.claude/state` or `CC_LMNR_STATE_DIR`) holds only numbers: `offset` = byte offset of the first turn not exported yet (or the end of the last row read), `exported` = starts of later turns already exported, `turnCount`, plus the tool-set timeline (`toolsScannedTo`, `toolSetChanges`). Every run re-reads the transcript from `offset`, splits it into turns at real prompts, exports the ready ones, and moves `offset` to the first turn still waiting. A turn's identity across runs is the byte offset of its prompt row (the transcript is append-only; a shrunk file restarts from 0). Never store transcript rows in state: anything held is simply re-read.
- **Export is batched and progress is per turn.** app-server rejects request bodies over `HTTP_PAYLOAD_LIMIT` (5 MB by default, measured after gzip decompression, so compression doesn't help), and a long turn repeats its growing history on every LLM span (real turns reach 35 MB). `exportInBatches` sends each run's spans in turn order in requests under `MAX_BATCH_BYTES` (4 MB) and stops at the first failed request; turns whose spans all went out count as exported, and the offset stops at the first turn that didn't (it and everything after are re-rendered and retried next run). Never go back to one request per run: an oversized batch fails identically on every retry and silently stops the session from ever exporting again. A single generation's `gen_ai.input.messages` is capped at 2 MB (`boundedHistoryJson`: oldest messages after the prompt give way to an "[N earlier messages omitted]" note) so no single span can exceed a request. A per-turn render exception is different: that turn's spans are discarded and it is skipped for good (not counted in `turnCount`), because a malformed turn would fail identically on every retry. Delivery is at-least-once: a failure mid-turn re-sends that whole turn next run, and if the state write fails after a successful export (`saveState` only logs), the next run re-exports — duplicating beats silently losing data.
- Each session's state file is guarded by an O_EXCL lock file (`<key>.lock`), so an overlapping Stop + SessionEnd can't export the same turns twice. A run holds it through all its export requests, so the holder touches it every 5 s (`LOCK_HEARTBEAT_MS`) and only a lock untouched for 30 s — left by a killed run — is taken over; the file holds the holder's token, so a run never touches or removes a lock it lost. A Stop run waits up to 10 s for it (Claude Code waits on Stop hooks, and anything skipped goes out next run); SessionEnd, the last chance to export, waits up to 60 s (`LOCK_WAIT_SESSION_END_MS`) so a slow Stop export doesn't make it give up and drop the waiting turns. Pinned by `tests/state.test.ts`. Session files untouched for 30 days are pruned when a new session starts.
- **Background tasks.** A turn whose Agent/Task call returned an async launch (`toolUseResult.status == "async_launched"`, or the launch text on old versions) waits until a task-notification for that tool_use is delivered, or SessionEnd (or after `MAX_REREAD_BYTES` of transcript since `offset`). "Delivered" means a user row (`<task-notification>…` / `origin.kind == "task-notification"`) or a `queued_command` attachment with `commandMode: "task-notification"` (how Claude Code hands it over mid-turn). Claude Code's `queue-operation` rows carry the same XML but are queue bookkeeping written BEFORE the model sees anything (and out of timestamp order) — never treat them as notifications, or the turn is emitted before Claude's reply to the report and that reply is lost. A notification that lands after the user's next prompt is moved (`routeNotifications`) into the turn whose tool_use it names (by `<tool-use-id>`, or `<task-id>` → agentId via the subagent `meta.json`). Rows Claude writes answering an `<agent-message>` before any new prompt simply belong to the waiting turn, since nothing has been cut at a run boundary.
- **LLM span inputs follow transcript order.** `render.ts` walks a turn's rows once: assistant rows sharing `message.id` merge into one message at its first row's position; everything the model receives between two assistant messages forms one input run, rendered as one user message of `tool_result` blocks (call order, then background reports — a task's last notification counts) followed by any injected isMeta user messages (e.g. `<agent-message>`, the `[Image: …]` note after an image Read). Each generation's input is the history before it and it starts when its last input arrived. Skill instructions (isMeta with `sourceToolUseID`) are not model input here; they go on the Skill tool span only with `CC_LMNR_CAPTURE_SKILL_CONTENT`.
- Subagents render directly under the tool span that launched them, starting at that tool_use's time; span creation order doesn't matter, only timestamps. Nested subagents' transcripts sit flat in the same `subagents/` directory, keyed by the launching tool_use id; `renderSubagent` passes the map down minus its own entry, so no descendant maps back to an ancestor. A **forked** subagent (`meta.json` `agentType: "fork"`) has no plain prompt: its transcript opens with a `fork-context-ref` row, a copy of the parent's Agent call, and a `tool_result` row carrying the fork instructions; that first user row opens its first turn.
- **Incomplete trailing turn:** Claude Code fires `Stop` before it writes the turn's final assistant row — measured 60–80 ms later in headless `claude -p`, and in interactive sessions often only after the hook exits, so waiting inside the hook doesn't help. The last turn therefore waits (`isIncomplete`) when (a) its prompt has no assistant row yet, (b) its last chat row is a `tool_result`, or (c) no assistant row since the last tool_result carries the end of the Stop payload's `last_assistant_message` (`finalAssistantText`; the final message can span rows, so a row's text must be a suffix). It goes out on the next run that sees it complete, or at SessionEnd, which never waits. Pinned by the "incomplete trailing turn (flush race)" tests.
- `readLines` parses a final line without a trailing newline when it is valid JSON (a partially written row never is), and otherwise resumes at its start next run.
- **Upgrade path:** versions before the commit-offset design kept one shared `<stateDir>/lmnr_state.json` with a read offset and raw held rows. When a session has no state file yet, `migrateLegacyState` resumes at the earliest held turn's prompt (found by row `uuid`) and marks every later prompt the old version had read as exported, so upgraded sessions neither re-export history nor drop held turns. Remove it once no pre-upgrade sessions can remain.
- State keys are camelCase (purely local); wire names keep their required forms: `gen_ai.usage.*`, Anthropic `tool_use_id`/`is_error`/`stop_reason`, `lmnr.*`.
- Keep `processTranscript`'s test seams (`exportFn` — called once per batch — / `renderFn` in `RunOptions`): ESM can't monkeypatch imported bindings, so these are how tests simulate export/render failure.
